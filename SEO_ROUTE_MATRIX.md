Snapshot date: 2026-09-15 (branch `munis-dev`).

**Methodology notes, stated once here rather than repeated per row:**

- **H1** is derived from each route's own `title` (the page-specific part before " | {brand}"), which is sourced from the same `xHero.h1` content object the page renders as its visible H1, for every route following this repo's established `${xHero.h1} | ...` title-building convention. This is a structural guarantee, not a per-row screen-read, except for the 14 EN routes ATS-SEO-121 actually verified directly (marked below) and the accident/home pages, which use custom title strings rather than a shared hero.h1 (spot-checked directly against their page.tsx JSX instead).
- **Primary/secondary keyword cluster**: only the 5 routes with a real Ahrefs Keywords Explorer/SERP Overview pull on record (ATS-SEO-004) get a cluster with real volume/KD figures. Every other row says "Not Ahrefs-validated" rather than inventing a number — per this ticket's own instruction not to include data not already present in the repository. No route has a distinctly-tracked _secondary_ cluster in the current evidence, so that column reads "Not tracked in repository" throughout; a route's full validated cluster (where one exists) is described in full under Primary.
- **Inbound/outbound links** are described per page-family pattern (nav mega-menu structure, hub-page grids, shared CTA), not individually re-traced link-by-link for all 121 rows — accurate to the actual `content/site.ts` nav config and hub components, but a family-level statement, flagged as such.
- **Raw HTML verified / Meta SEO Inspector checked / SEO Meta in 1 Click checked**: "Yes" only for the exact routes ATS-SEO-121 actually inspected (14 for raw HTML via `curl`, 12 for the two browser extensions, both EN-only). Every other route — including every ES/PT/HT page and every service-area city page beyond Boca Raton/Miami — genuinely reads "No": not yet individually checked, not assumed clean.
- **Ahrefs issue status** reflects the 15 Sep 2026 Site Audit recrawl (ATS-SEO-122), which is aggregate/site-wide (22 errors, all "Image file size too large") — the export does not itemize which specific URLs carry which issues, so this column states the aggregate finding rather than a fabricated per-URL breakdown. ES/PT/HT pages are outside that recrawl's scope entirely.
- `/thank-you`, `/es/gracias`, admin routes, and `/blog/[slug]` (no articles published yet) are intentionally absent — none are registered SEO routes (the first two are noindex-by-design, the codebase's own `content/seo.ts` comment says so explicitly; the last has zero live instances to enumerate).
- **Correction (ATS-SEO-132 evidence pass, 2026-09-16)**: the original generation grepped only each route's own `page.tsx` for schema-builder imports, which missed `BreadcrumbList` on 7 rows (`/conditions/back-pain`, `/neck-pain`, `/cervicogenic-headache`, `/concussion`, `/tmj-jaw-pain`, and — already correctly shown — `/sciatica`/`/whiplash`) because `HeroSolidPanel` renders `BreadcrumbJsonLd` itself whenever a `breadcrumbs` prop is passed, not the page. Confirmed by curling the live production build and parsing the actual JSON-LD (`SEO_QA_EVIDENCE/raw-html/SUMMARY.md`).
- **Fixed (2026-09-16, same-day follow-up)**: all 7 `/conditions/*` pages now render `MedicalWebPage` (the gap the correction above left standing) — see `lib/schema.test.ts`'s new source-scan regression test. Also fixed a real bug the same investigation surfaced: `/conditions/sciatica` and `/conditions/whiplash` were each emitting `BreadcrumbList` **twice** (once from `HeroSolidPanel`, once from an explicit page-level `<BreadcrumbJsonLd>` call) — the duplicate call is removed, guarded by a second new regression test. `/services/cupping-therapy` also gained a `Service` entity, matching its `/services/*` siblings.
